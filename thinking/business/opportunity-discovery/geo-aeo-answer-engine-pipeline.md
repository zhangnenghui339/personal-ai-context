## 定位

在「搜索 → 答案引擎」的范式迁移中，做一套**结构化内容生产 + 多答案引擎分发 + 归因闭环**的基础设施：

- 把企业内容（产品、案例、FAQ、文档）转成「AI 可理解的结构化知识」；
- 针对各类答案引擎（Google AI Overview、Perplexity、各类垂直助手）做适配与分发；
- 追踪「被引用 → 点击 → 转化」的全链路归因；
- 提供持续优化建议（哪些内容被引用多、哪些被忽略、如何改写）。

不与巨头拼大模型或检索算法，在卡口做**内容装卸（结构化）、协议适配（多引擎分发）、验票门禁（被优先引用的博弈）、记账（归因）**。

## 在本库模型里的位置

| 维度 | 判断 |
|---|---|
| 势能形态 | **卡口型**——坐在「企业内容 → 答案引擎 → 客户决策」的必经中转位；不生产内容、不生产模型，收适配与归因的过路费 |
| 势差来源（7 点） | 命中「入口搬家（搜索页 → 答案卡片）」「无中生有（AI 引用博弈是全新数据空间）」「巨头买单（答案引擎需要高质量结构化语料）」 |
| 押不变 | 「被目标客户在决策时看到并信任」是 10 年不变的绝对需求；变的只是介质 |
| 占有层 | 结构化内容库 + 分发关系 + 历史归因数据构成迁移成本；`where-distribution-is-going.md` 句 3——拥有的是「下一期仍会分配新注意力的那一层」的适配与归因权 |

## 10 年不变需求

- 企业永远需要「被目标客户在决策时看到并信任」；
- 介质从「搜索结果页」变成「答案卡片 / 对话引用」，但「被看见 + 被信任」的本质不变；
- 只要 AI 参与信息筛选，就有「如何被 AI 优先引用」的博弈。

判据（10 年后客户会不会要它的反面）：没有企业会要「更不被目标客户看到、更不被信任」——绝对需求，不是偏好。

## API 化方式

| 端点 | 作用 |
|---|---|
| `POST /v1/assets` | 上传 / 更新内容资产（自动结构化） |
| `GET /v1/distribution/status` | 查看在各答案引擎的收录与引用情况 |
| `POST /v1/experiments` | 创建 A/B 版本（不同结构化策略） |
| `Webhook` | 引用事件、流量事件、转化事件回调 |
| `GET /v1/attribution` | 归因分析 API |

价值 100% 在软件与协议里，无重人力交付。

## 数字码头属性（活数据系统，非静态存储）

- **结构化内容库**：企业知识资产的「AI 版本」；
- **各答案引擎的分发配置与历史**：适配策略、收录状态、引用记录；
- **引用与转化归因数据**：被引用 → 点击 → 转化的全链路；
- **内容迭代历史与效果数据**：哪个版本、哪种结构化策略带来多少引用与转化。

不是用完即走的轻量工具，也不是纯 Notes / 纯 Markdown 存储——锁定的是**动态状态（收录 / 引用 / 转化流转）+ 联调配置（多引擎适配）+ 迭代效果历史**。

---

## 替换成本

- 内容资产已经按你的 schema 重构；
- 归因数据与分发关系都在你这里；
- 换系统 = 重新结构化 + 重新建立分发关系 + 丢失历史归因数据。

即：能带走的是原始内容，带不走的是**结构化 schema 的沉没投入、与各答案引擎建立的分发关系、以及无法重建的历史归因与实验效果数据**。

## 一句压缩

**搜索页变答案卡片，但「被目标客户看到并信任」10 年不变。在这个卡口做内容结构化、多引擎分发适配与全链路归因，按内容资产量 / API 调用 / 归因席位收租——套利会关（谁都能写结构化脚本），结构化库、分发关系与归因历史留下。**
